Quero implementar agora o fluxo de criação de conta para clientes que compraram um dos produtos pela Cakto.

Atualmente o webhook da Cakto já está funcionando e registra o plano comprado na tabela:

```text
cakto_entitlements
```

O entitlement é associado ao e-mail normalizado da compra e possui:

```text
essential
deluxe
```

O produto de upgrade apenas altera `essential → deluxe`.

Nesta etapa, quero integrar esse entitlement ao fluxo de autenticação do app.

IMPORTANTE: revise primeiro a implementação atual de autenticação, Firebase e banco antes de alterar qualquer coisa. Reutilize a arquitetura existente e não crie um segundo sistema de autenticação.

---

# 1. Fluxo desejado

O fluxo deve funcionar assim:

```text
Cliente compra na Cakto
↓
Webhook registra entitlement pelo e-mail
↓
Cliente acessa o app
↓
Cria uma conta usando o mesmo e-mail utilizado na compra
↓
Sistema verifica se existe um entitlement válido para esse e-mail
↓
Se existir, permite criar a conta
↓
Conta Firebase criada normalmente
↓
Plano é associado/reconhecido automaticamente
↓
Usuário entra no app com acesso correspondente ao plano
```

NÃO quero criar automaticamente uma conta Firebase no momento da compra.

NÃO quero criar senha default.

O cliente deve escolher sua própria senha no fluxo normal de registro.

---

Anteriormente pedi para bloquear/desabilitar a página de registro.

Agora essa decisão deve ser revertida.

Restaure a página/rota de registro para que compradores possam criar suas contas.

* bloqueada
* redirecionando para login
* desabilitada
* inacessível

Restaure esse acesso.


# 4. Cadastro NÃO deve ser aberto para qualquer e-mail

Apesar de restaurarmos a página de registro, apenas clientes que possuem um entitlement da Cakto devem conseguir criar conta.

Antes de criar o usuário no Firebase, valide o e-mail informado no registro.

Normalize o e-mail exatamente da mesma forma utilizada pelo webhook:

```ts
email.trim().toLowerCase()
```

Depois consulte:

```text
cakto_entitlements
```

Se existir entitlement para esse e-mail:

```text
permitir cadastro
```

Se NÃO existir:

```text
não criar usuário Firebase
```

e mostrar uma mensagem amigável.

Exemplo conceitual:

```text
Não encontramos uma compra vinculada a este e-mail.

Use o mesmo e-mail informado no momento da compra.
```

Não precisa usar exatamente esse texto se o projeto já tiver um padrão melhor de mensagens.

---

# 5. Segurança da validação

A validação do entitlement NÃO pode depender apenas do frontend.

Não faça algo como:

```ts
if (frontend encontrou plano) {
   firebase.createUser(...)
}
```

A existência do entitlement deve ser validada de forma segura pelo backend/API antes ou durante o processo de criação da conta.

O frontend pode consultar o resultado, mas não deve ser a fonte de verdade.

---

# 6. Criação da conta

Quando existir entitlement válido:

o usuário deve poder criar sua conta utilizando o fluxo normal do Firebase Authentication.

Preserve os campos atualmente utilizados pelo registro, como:

* nome, se já existir
* e-mail
* senha
* confirmação de senha, se existir

Não crie senha automática.

Não envie senha por webhook.

Não armazene senha fora do Firebase Authentication.

---

# 7. Vínculo com o plano

Depois que a conta Firebase for criada com sucesso, o sistema deve reconhecer automaticamente o entitlement correspondente ao e-mail.

Exemplo:

```text
compra Essential
↓
cakto_entitlements = essential
↓
cria conta com mesmo e-mail
↓
usuário autenticado passa a possuir acesso Essential
```

E:

```text
compra Deluxe
↓
cakto_entitlements = deluxe
↓
cria conta com mesmo e-mail
↓
usuário autenticado passa a possuir acesso Deluxe
```

Não copie ou recrie regras de plano desnecessariamente.

A tabela `cakto_entitlements` deve continuar sendo a fonte de verdade para a compra realizada pela Cakto, a menos que a arquitetura existente possua uma forma mais apropriada de vincular isso ao usuário Firebase.

---

# 8. Usuário que já possui conta

Esse cenário é muito importante.

Se uma pessoa já tiver uma conta Firebase e posteriormente realizar uma compra utilizando o mesmo e-mail:

```text
conta já existe
↓
Cakto registra/atualiza entitlement
↓
usuário continua usando a mesma conta
↓
novo plano deve ser reconhecido automaticamente
```

Não crie uma segunda conta.

Não exija novo cadastro.

Não altere senha.

Na próxima autenticação, atualização da sessão ou consulta de entitlement, o usuário deve receber o acesso correspondente ao plano adquirido.

---

# 9. Caso tente registrar e a conta já exista

Se o e-mail possuir entitlement, mas já existir uma conta Firebase para ele, não tente criar outra conta.

Mostre uma mensagem apropriada e direcione o usuário para login.

Exemplo conceitual:

```text
Já existe uma conta com este e-mail.
Entre na sua conta para acessar seu conteúdo.
```

Se houver fluxo de recuperação de senha no projeto, preserve-o.

---

# 10. E-mail diferente da compra

Se o cliente comprou com:

```text
cliente@email.com
```

mas tentar registrar:

```text
outro@email.com
```

o cadastro deve ser recusado porque não existe entitlement para esse segundo e-mail.

Não tente inferir que são a mesma pessoa.

Não mova entitlement automaticamente entre e-mails.

A mensagem deve orientar o cliente a utilizar o mesmo e-mail informado na compra.

---
