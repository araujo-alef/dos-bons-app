Hoje o sistema só processa purchase_approved e altera diretamente cakto_entitlements de forma monotônica.

Quero evoluir isso para que o entitlement seja recalculado a partir das compras válidas, sem quebrar os fluxos atuais.

IMPORTANTE:
- preservar autenticação do webhook;
- preservar idempotência;
- preservar locks/concurrency;
- preservar registration-eligibility;
- preservar /api/me/plan;
- preservar frontend;
- não alterar checkout;
- não alterar Firebase Auth;
- não remover comportamento atual de purchase_approved;
- manter os product IDs de produção já configurados.

==================================================
OBJETIVO
==================================================

Passar a tratar:

- purchase_approved
- refund
- chargeback

purchase_refused continua sem conceder acesso e pode continuar sem efeito no entitlement.

A regra principal deve ser:

o plano atual do usuário deve ser DERIVADO das compras válidas daquele e-mail.

Não aplicar downgrade diretamente baseado apenas no evento recebido.

==================================================
REGRA COMERCIAL DOS 3 PRODUTOS
==================================================

Temos 3 produtos:

ESSENTIAL
→ representa acesso Essential

DELUXE
→ representa acesso Deluxe direto

UPGRADE
→ é um complemento do Essential
→ sozinho NÃO representa uma compra Deluxe completa

A regra correta é:

- Deluxe pago → deluxe
- Essential pago + Upgrade pago → deluxe
- somente Essential pago → essential
- somente Upgrade pago → essential
- nenhuma compra válida → null

Portanto, o Upgrade NÃO deve ser tratado como um grants_plan = deluxe independente.

==================================================
PURCHASE_APPROVED
==================================================

Quando chegar purchase_approved:

1. autenticar
2. validar payload
3. resolver product.id
4. localizar a compra por data.id
5. criar ou atualizar a compra como status = paid
6. recalcular o entitlement do e-mail
7. manter idempotência
8. responder 200

Não alterar diretamente plan de forma incremental sem olhar o conjunto de compras válidas.

==================================================
REFUND
==================================================

Quando chegar refund:

1. autenticar normalmente
2. identificar a transação original pelo identificador correto enviado pela Cakto
3. localizar a compra persistida
4. atualizar:
   status = refunded
5. salvar refunded_at, se disponível
6. recalcular o entitlement daquele e-mail
7. preservar histórico da compra

Não excluir a compra.

Se a transação original não for encontrada:
- não inventar associação por preço, nome ou e-mail apenas;
- logar código controlado;
- responder de forma segura;
- não alterar entitlement indevidamente.

==================================================
CHARGEBACK
==================================================

Mesma lógica do refund:

1. localizar a compra original
2. status = chargeback
3. salvar chargedback_at, se disponível
4. recalcular entitlement
5. preservar histórico

==================================================
FUNÇÃO CENTRAL DE RECÁLCULO
==================================================

Criar uma função central, por exemplo:

recalculateEntitlement(email)

Ela deve consultar apenas compras com:

status = paid

A partir delas, calcular:

const hasEssential = existe compra essential paga
const hasDeluxe = existe compra deluxe paga
const hasUpgrade = existe compra upgrade paga

Regra:

if (hasDeluxe) {
  return "deluxe";
}

if (hasEssential && hasUpgrade) {
  return "deluxe";
}

if (hasEssential || hasUpgrade) {
  return "essential";
}

return null;

Essa é a regra comercial oficial nesta etapa.

==================================================
IMPORTANTE SOBRE UPGRADE
==================================================

O Upgrade é dependente do Essential para formar Deluxe.

Ou seja:

Essential + Upgrade
→ Deluxe

Se qualquer um dos dois deixar de estar pago:
→ cai para Essential

Exemplos:

Essential paid
Upgrade paid
Refund Essential
→ essential

Essential paid
Upgrade paid
Refund Upgrade
→ essential

Não retornar null nesses casos.

Também não tratar Upgrade sozinho como Deluxe.

==================================================
DELUXE DIRETO
==================================================

Uma compra direta do produto Deluxe é independente.

Deluxe paid
→ deluxe

Se essa compra for refund/chargeback:
- recalcular com base nas outras compras válidas.

Exemplo:

Essential paid
Deluxe paid
Chargeback Deluxe
→ essential

Outro:

Essential paid
Upgrade paid
Deluxe paid
Chargeback Deluxe
→ deluxe

porque Essential + Upgrade ainda formam Deluxe.
